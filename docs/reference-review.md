# Legacy PHP reference review

All four uploads were reviewed in their supplied `(2)` versions. The project has its own SQLite schema and uses the references for workflow and field selection.

| Reference | Observed workflow | Missing dependencies or ambiguity |
| --- | --- | --- |
| `add-product(2).php` | A multipart form captures the product name and code, merchant code, category, manufacturer, price and costs, description, status, availability, images, barcodes and other catalogue fields. A browser validation function checks required fields and code syntax. PHP checks for an existing product code, creates a product and may write stock tracking, SKU, image and barcode records. | Requires the legacy schema and shared includes, `SimpleImage.php`, upload directories and other scripts. Database uniqueness and complete server-side validation cannot be established from the upload. |
| `add_stock(2).php` | Selects a product by code and an inventory type. If the combination is absent, it inserts a `products_copy` row with the submitted absolute quantity in both availability and actual quantity, records a `Product_Add` entry and can update pricing on related inventory records. The existing-pair branch reports a duplicate. | The visible operation creates a new inventory record. It neither adds to nor replaces the existing pair's quantity. Other inventory adjustment routes and inventory configuration are outside the supplied files. |
| `urns-add-orders(2).php` | Checks for an existing transaction reference by region, writes an order and customer information, creates line and inventory records, selects and sometimes splits quantities across inventory pools, deducts availability and handles shipping-related values. | Price rules rely on regional inventory constants and legacy tables. The visible SQL runs as separate statements with no explicit transaction around them, so all-or-nothing behaviour and full stock guarantees cannot be inferred. |
| `urns-orders(2).php` | Lists and filters orders by status and other criteria. It shows placed, processed, dispatched and part-dispatched orders, cancellation and other labels, plus tracking states such as delivered and in progress. It links to order details, status editing, dispatch notes, and bulk dispatch or print actions. | Linked action handlers such as `edit-order-status.php` and the dispatch scripts were not supplied, so cancellation and restocking behaviour cannot be established. A cancellation comparison includes an assignment in the condition, making that display branch unreliable as a source of status rules. |

The files depend on `Include/SessionCheck.php`, `Include/DatabaseConnection.php`, `Include/Functions.php`, legacy templates and JavaScript, and a MySQL schema using the old `mysql_*` API. The new app uses one inventory pool and one GBP sale price per SKU. It captures only the customer name and uses Open and Cancelled order statuses. Legacy images, pricing tiers, payment and dispatch fields, and customer records are outside this phase.
